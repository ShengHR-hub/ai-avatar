# AI Avatar Studio V1.0 Task Cards 与工作分工

> 状态：已被 `docs/task-cards/00-index.md` 和 `docs/task-cards/LEAD-*`、`ENG-*` 取代
> 日期：2026-09-24
> 目的：把已冻结的架构和路线图转换为可执行的工程任务，并明确技术负责人和工程开发 Agent 的边界。

## 1. 当前阶段判断

项目现在进入**正式开发阶段**。本文件保留为早期差异盘点参考；正式执行以 `docs/task-cards/00-index.md` 及各独立任务卡为准。旧测试版不构成 V1.0 的实现前提。

当前代码与冻结架构存在基础差异：

| 领域 | 当前代码基线 | V1.0 冻结基线 | 处理方式 |
|---|---|---|---|
| Web/API | Next.js Route Handler | Next.js 前端 + FastAPI REST API | 先建立 API 边界，再迁移业务入口 |
| 数据库 | SQLite + Drizzle | PostgreSQL + SQLAlchemy/Alembic | 先完成 schema 与迁移契约，再迁移数据访问 |
| 异步任务 | 数据库任务表 + Node Worker | Redis + Celery Worker/Beat | 保留任务表事实源，替换调度执行层 |
| 本地存储 | Local Adapter，兼容 COS | MinIO Adapter，生产 COS/OSS/S3 | 保持 Storage Adapter 接口不变 |
| AI 调用 | Provider Router 已有初版 | AIProvider + ProviderRouter + Mock/Primary | 先补齐统一状态、错误、成本和幂等 |

因此，工程 Agent 不得把现有代码直接“改成另一套架构”而不经过卡片验收。每一张迁移卡必须有边界、迁移策略和回滚方式。

## 2. 角色分工

### 2.1 技术负责人（本任务主 Agent）

负责：

- 技术架构和技术选型；
- 数据库模型、迁移策略和事务边界；
- OpenAPI、错误码、状态机和幂等契约；
- 点数预留、消费、释放和退款规则；
- Provider 与 Storage Adapter 接口；
- Task Card 编写、依赖排序和范围控制；
- 对工程 Agent 的代码进行审核；
- 设计异常场景、集成测试和验收；
- 决定是否允许进入下一张卡。

技术负责人不承担大批量页面、CRUD 或普通适配代码的实现。

### 2.2 工程开发 Agent（国产模型）

负责：

- 按 Task Card 实现前端页面和组件；
- 按契约实现 FastAPI、Repository、Service 和普通 CRUD；
- 实现数据库迁移、Provider/Storage 适配器和 Worker 任务；
- 编写卡片要求的单元、集成和 E2E 测试；
- 修复常规 Bug；
- 每张卡完成后提交改动文件、测试结果和风险说明。

工程 Agent 禁止：

- 自行更换框架、数据库、队列或部署方式；
- 自行修改任务状态机、点数规则或退款条件；
- 在当前卡片中增加社区、支付、推荐等范围外功能；
- 绕过 Service 直接写账务表或调用 Provider SDK；
- 把“接口接受参数”写成“能力已验证”。

## 3. 执行规则

1. 工程 Agent 开始每张卡前，必须阅读本文件、对应架构文档和 API 契约。
2. 卡片按依赖顺序执行；同一时刻只允许一张涉及账务或任务状态的卡进入实现。
3. 卡片完成后，工程 Agent 先自测并报告，技术负责人审核后才能进入下一张卡。
4. 发现契约冲突时暂停实现，提交问题和最小选项，由技术负责人决定。
5. 任何跨架构的改变都必须先更新架构文档和卡片，再开始编码。

## 4. Task Card 总览

### T00：工程基线与迁移边界

**负责人：** 技术负责人设计，工程 Agent 实现。

**目标：** 明确 V0.1 代码如何逐步进入 V1.0 单仓库结构，保证每一步可运行、可回滚。

**依赖：** 无。

**允许修改：** `README.md`、`docs/architecture/*`、`docker/`、`frontend/`、`backend/`、`shared/`、`scripts/`、CI 配置。

**输入：** 当前 V0.1 代码、01-07 架构文档、环境变量模板。

**输出：** 目标目录、进程启动方式、迁移策略、开发命令和差异清单。

**验收：** 文档明确哪些代码复用、哪些代码迁移、哪些代码暂时保留；不能出现两套未说明的事实源。

**不做：** 不新增产品功能，不接入真实支付，不部署生产环境。

### T01：数据库 Schema 与迁移基线

**负责人：** 技术负责人定义模型和不变量，工程 Agent 实现 SQLAlchemy/Alembic。

**目标：** 建立 PostgreSQL schema，覆盖用户、邀请码、钱包、点数流水、生成任务、媒体资源、Prompt、风格、订单预留、Provider 调用和审计日志。

**依赖：** T00。

**重点不变量：** UUID 主键；UTC 时间；点数为整数；流水追加写；`available_points`、`reserved_points` 与流水可核对；同一生成任务最多一条最终 `CONSUME` 或 `RELEASE`。

**测试：** 空库迁移、重复迁移、唯一约束、并发预留失败、账务流水一致性。

**不做：** 支付网关和多地区分库。

### T02：认证、邀请码与用户资料

**负责人：** 工程 Agent。

**目标：** 实现邀请码兑换、邮箱绑定、稳定用户身份、用户资料和会话。

**依赖：** T01。

**接口：** `POST /api/v1/invites/redeem`、`GET /api/v1/me`、`PATCH /api/v1/me`。

**测试：** 邀请码过期、已兑换、并发兑换、重复请求、邮箱绑定恢复、越权访问。

**不做：** 手机验证码、微信登录、OAuth。

### T03：Points Service 与账务幂等

**负责人：** 技术负责人审核规则，工程 Agent 实现。

**目标：** 实现增加、预留、消费、释放、退款的统一 Service，禁止其他模块直接改钱包余额。

**依赖：** T01、T02。

**固定流程：**

```text
预留：available -= cost，reserved += cost，写 RESERVE
成功：reserved -= cost，写 CONSUME
明确失败：reserved -= cost，available += cost，写 RELEASE
UNKNOWN/NEEDS_REVIEW：保持 RESERVED，等待人工决定
```

**测试：** 重复幂等键、并发预留、重复成功回调、失败后重复退款、余额不足、事务回滚。

**不做：** 不调整产品点数价格，不开发支付。

### T04：Storage Adapter 与上传生命周期

**负责人：** 工程 Agent。

**目标：** 统一本地 MinIO、测试存储和生产 COS/OSS/S3 的上传、读取、短期签名和删除接口。

**依赖：** T01、T00。

**测试：** 文件类型、大小、哈希、可解码性、权限、过期删除、签名 URL 失效。

**不做：** 不把图片二进制存入 PostgreSQL，不开放任意对象路径访问。

### T05：Generation Service 与任务状态机

**负责人：** 技术负责人冻结状态转换，工程 Agent 实现。

**目标：** 创建异步任务、预留点数、保存输入引用、恢复任务和查询历史。

**状态：** `CREATED → QUEUED → PROCESSING → SUCCESS | FAILED | NEEDS_REVIEW`。

**依赖：** T03、T04。

**测试：** 幂等创建、非法状态转换、刷新恢复、Worker 重启恢复、超时、结果缺失、权限隔离。

**不做：** 不在 API 请求进程中同步执行 AI 生成。

### T06：MockProvider、队列与 Worker 闭环

**负责人：** 工程 Agent。

**目标：** 使用 Redis + Celery 完成本地可重复的生成闭环，不产生真实 AI 费用。

**依赖：** T05、T04。

**Mock 场景：** 成功、延迟、失败、超时、UNKNOWN、成功但无图片、重复回调。

**测试：** 队列重试、指数退避、任务恢复、重复消费、成功消费点数、失败释放点数、异常进入 `NEEDS_REVIEW`。

**不做：** 不用 Mock 结果宣称真实 Provider 能力已验证。

### T07：PrimaryProvider 与 Provider 审计

**负责人：** 技术负责人审核 Provider 契约，工程 Agent 实现适配器。

**目标：** 接入一个主供应商，统一同步/异步、轮询/Webhook、错误分类、调用记录和成本记录。

**依赖：** T06。

**必须记录：** Provider、模型、外部请求 ID、耗时、输入输出用量、图片数量、估算成本、币种和脱敏元数据。

**测试：** 超时、限流、鉴权失败、供应商成功但无图片、重复 Webhook、切换 Provider 不改业务层。

**不做：** 不做自动多模型路由，不把密钥暴露给前端。

### T08：前端 API Client 与生成工作流

**负责人：** 工程 Agent，技术负责人审核交互与契约。

**目标：** 通过 OpenAPI 生成或维护客户端，完成上传、模式选择、风格/Prompt、创建任务、轮询、离开后恢复和结果页。

**依赖：** T02、T04、T05、T06。

**测试：** 移动端上传、弱网重试、刷新恢复、错误码展示、余额不可用时阻止提交、服务端密钥不进入 bundle。

**不做：** 不在页面直接写 API URL 或重复实现轮询。

### T09：分享、下载、反馈与资源清理

**负责人：** 工程 Agent。

**目标：** 完成非公开分享、短期下载、反馈提交、原图和结果生命周期清理。

**依赖：** T04、T05、T08。

**测试：** 分享权限、撤销、过期、跨设备访问、下载失败、重复反馈、清理任务幂等。

**不做：** 不做公开 UGC 社区和推荐流。

### T10：端到端验收与回归测试

**负责人：** 技术负责人设计测试，工程 Agent 修复失败项。

**目标：** 验证本地完整闭环和关键资金安全场景。

**依赖：** T02-T09。

**必须覆盖：** 邀请码 → 邮箱 → 点数 → 上传 → 创建任务 → Worker → Provider → 存储 → 结算 → 结果 → 下载/分享/反馈；以及失败退款、UNKNOWN、重复回调、Worker 重启和越权访问。

**验收：** 类型检查、构建、迁移、API 契约、集成测试和 E2E 全部通过；失败项必须有记录和处理决定。

### T11：测试服务器部署准备

**负责人：** 技术负责人制定部署门槛，工程 Agent 编写部署配置。

**目标：** 仅在 T10 通过后准备单服务器 Docker Compose、Nginx、HTTPS、托管 PostgreSQL、对象存储、备份和监控。

**依赖：** T10。

**不做：** 不提前引入 Kubernetes、微服务或多机自动扩缩容。

## 5. 当前立即执行的卡片

工程 Agent 当前只执行 **T00：工程基线与迁移边界**，完成现状差异清单后等待技术负责人审核。审核通过后按 T01 → T03 → T04 → T05 → T06 顺序推进；T07 及以后必须以本地 Mock 闭环通过为前置条件。

技术负责人当前工作：

1. 审核 T00 差异清单；
2. 冻结 T01 数据库字段和约束；
3. 冻结 T03 点数 Service 接口和状态转换；
4. 设计 T06 的异常测试矩阵；
5. 审核每张卡的代码和测试结果；
6. 决定是否允许进入下一张卡。

## 6. 卡片回报格式

工程 Agent 完成每张卡后，必须按以下格式报告：

```text
Task Card：Txx
改动文件：
实现内容：
接口/迁移变化：
测试命令与结果：
未完成事项：
架构风险或需要确认的问题：
```

没有这份回报和技术负责人审核，不得把卡片标记为完成。
