# AI Avatar Studio V1.0 产品主线

> 最新裁决：2026-09-29（产品方向纠偏）。本文记录当前 V1.0 的产品目标。
> 历史 V0.1 测试版不是当前实施基线；早期"真人照片转绘、尽量保留本人特征"的定位
> **已被本版取代**，不要再按那个口径写文案或验收。
> 来源：用户当前明确要求，以及其提供的早期产品讨论。早期对话中的助手建议仅作背景，
> 不能覆盖现行冻结契约。

## 核心目标

帮用户创作**任意类型的头像**——人物、虚构角色、宠物、手绘形象、情绪风景、背影、玩偶、
抽象画面都可以。用户进入网站后应立即看懂"我能做什么"，并能顺畅走完选择方式、写描述、
生成、等待、查看两张结果、下载的流程。技术、账户和点数规则由系统承担，不应主导首次使用体验。

**不再**以"真人照片转绘成像本人的头像"为中心。是否保留五官相似度由用户自己的描述决定，
产品不承诺、也不以此作为卖点。

## 三项能力

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 文字创作 | **可用** | 不上传图片，直接用描述生成；每次返回两张 |
| 改造我的图片 | **可用** | 上传一张自己的图片，结合描述进行改造。人物、宠物、玩偶、静物、风景都可以；原来的"照片转绘"只是它的一个用例 |
| 参考图片找灵感 | **可用**（`ENABLE_IMAGE_ANALYSIS` 控制，默认关） | 上传喜欢的参考图片，由视觉模型提取近似的画面描述，用户修改后再生成自己的头像 |

第三项的口径（不可越界）：

- 它是**"描述图片以获得创作灵感"**，不是恢复原作者的原始提示词，也不能承诺精确复刻；
- 它**不等于** `REFERENCE_IMAGE` 生成能力：后者是把参考图作为条件送进生成，本项只是先读出描述、
  再由用户自己发起一次普通的文字或图片生成。把两者混为一谈是错的；
- 界面上必须写清楚"这段是模型看你这张图**现写**的描述，可以改"，不得让它看起来像
  从图里"还原"出来的原文；
- 描述结果不长期保存：只在服务端短期缓存（同一张图重复点击不再重复付费），不入库、不进日志；
- 一次分析就是一次真实付费调用，因此有每日配额与同图去重；配额状态未知时宁可拒绝，
  不能"看不见额度就继续花钱"。

## 前端体验

- 首页是可进入创作的产品页：顶部有 Logo 和用户入口，中间是醒目的两个创作入口，
  **主视觉是本站真实产出的成品图**，下方是少量有代表性的灵感方向与明确入口。
- **作品图是视觉主角**：提示词不能压住图像主体。查看、复制、带入创作台编辑这些动作
  收在紧凑的控件与可展开面板里，不占画面中心。
- 首页只呈现**少量有代表性的方向 + 清晰入口**；完整的多维标签组合留在创作台，
  不得把全部标签铺满首页。
- 视觉方向为 Apple 毛玻璃风格（浅银灰、高透明）；整体简洁、高级。图片是第一视觉信号，
  不以密集表单作为首页主体，也不用"适合上传的示例照片"和空结果框充当作品展示。
- 文字创作与改造图片平级。灵感分类降低"不会写描述"的门槛；普通用户无需理解模型、Provider、
  任务状态机等内部概念。
- 创作台提供三个易懂入口，共享一个**始终可编辑**的描述区域；切换入口时保留草稿，
  不意外清空用户手写的描述。提交前显示实际使用的图片、描述和生成方式。
- 等待阶段说明任务仍在进行、允许离开或刷新后恢复；结果阶段优先展示两张成品，下载动作明确。
  异常状态使用用户能理解的文案，同时忠实反映服务端状态与点数结果。
- 未登录用户也应能浏览作品、灵感分类和生成方式。真正上传或提交生成时，
  仍遵守当前邀请码、邮箱验证、权限和点数契约。
- 手机端同样应能完成主要创作流程，不能只把桌面布局缩窄。

## 展示素材的诚实性

首页与作品区放的必须是**可核验来源**的图，规则如下：

1. 只有本站生成链路真实产出的成品才能作为"作品"展示，并须记录**来源**、
   **发布授权**，以及**实际提交过的提示词**；如果为了公开改写过，必须显式标注为公开改写版
   并说明原因，界面不得把两者混为一谈。
2. 纯文字生成的作品**不需要**配输入图。只有能证明属于同一次图片改造的素材，
   才可以展示"输入 → 结果"的成组关系；拿不出证据就只展示结果。
3. 第三方授权摄影素材、`ex/` 里来自小红书的外部参考图、私人测试产物，
   **一律不得冒充本站生成结果**。`ex/` 的公开授权未核实，只能用于内部观察，
   或在取得许可后另行展示。
4. 与其用别的图凑数，不如把位置留白并说明在等什么素材——但留白不是产品形态：
   拿到真实成品后应立刻替换掉空位表达。

## 灵感标签体系

- 用**可扩展、可组合**的内容目录取代"几个固定模板代表所有玩法"的做法。
  维度：主题（人物/虚构角色/宠物/风景/背影/玩偶/抽象/两个人）、表现（手绘/蜡笔/胶片/漫画/
  像素/黏土/拼贴/写实）、情绪（忧郁/治愈/搞怪/呆萌/冷感/神秘/松弛/热烈）、
  场景（海边/雪地/雨夜/森林/窗边/城市夜景）、光线、构图；用途作为一键套用的预设。
- 每个标签只产出一段**可编辑的描述片段**，写进描述框，用户仍然可以改字；
  **不得**向生成 API 增加未经契约支持的 `style_id`。
- 不使用受保护角色或 IP 的名称，不提供"复刻某个角色"的标签。
- 没有可核验的热度数据，所以栏目叫「灵感分类」，**不写"热门/热榜/实时"**。

## 当前实现边界

- 保留已完成的后端、数据库、OpenAPI、账务、存储和 Provider 契约；
  前端纠偏不构成重写 ENG-00 至 ENG-07 的理由。
- 冻结 OpenAPI 没有风格与灵感模板的读取接口；灵感标签只是前端静态目录 + 可编辑描述。
  分享与反馈已有契约路径，实施归属为 ENG-09。
- 「参考图片找灵感」的图片理解接口已按最小加法落进契约：`POST /api/v1/analyses`
  （要求 `Idempotency-Key`，返回一段可编辑的画面描述）。它不新增错误码、不新增数据库表、
  不加迁移，也不改变生成与账务的任何语义；能力由服务端 `ENABLE_IMAGE_ANALYSIS` 开关控制，
  默认关闭。付费口径与隐私口径见 `03-api-contract.md` 第 4.6 节与 `04-ai-provider.md` 第 2.1 节。
- 灵感标签的完整多维组合留在**创作台**；首页只保留少量代表方向与入口，避免把标签铺满页面。
- 已完成的功能验证不能代替产品验收。前端验收需确认：首次访问能理解用途、三种方式容易找到、
  作品展示可信、创作步骤简明、等待与结果清楚、手机端可用。

## 保留不变的技术与财务约束

- 生成仍走既有链路：文字创作 → `TEXT_PROMPT`；改造图片 → `PHOTO_PROMPT`（1 张 `SOURCE`）。
  任务状态机、点数预留/消费/释放、幂等、轮询与短期下载地址语义不变。
- 每次生成固定两张；提交时先占用点数，失败全额退回，需要人工确认时保持占用。
- 接口没有可靠价格字段时，**不得猜测本次价格**。
- 不得把真实密钥、真实用户图片或 Provider 原始响应写入仓库、日志或响应。
